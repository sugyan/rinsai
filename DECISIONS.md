# rinsai — decision log

What was decided, why, and — where the decision is conditional — what would have to be measured to revisit it. [DESIGN.md](./DESIGN.md) is the plan, [CLAUDE.md](./CLAUDE.md) is the rules, [CONVENTIONS.md](./CONVENTIONS.md) is what is frozen, [PROGRESS.md](./PROGRESS.md) is the state and the only home for measured numbers.

**Append-only in its conclusions.** An entry that is later overturned is marked superseded and kept; the reasoning is never edited away. What *may* be edited is a copied measurement: a number a decision rests on lives in PROGRESS.md's tables and is pointed at from here, never duplicated, and replacing a stale duplicate with its pointer is maintenance rather than revision. Two copies of a measurement drift, and this log has already done it once.

## The log

- **2026-08-04 — named `rinsai` (凛彩), in a new repository, depending on released versions of shunsai.**
  - **The name**: **R**ust **I**mplementation, **N**NUE **S**earch, for **AI**. It continues both family rules — the `-sai` ending, and the two-layer construction of a kanji reading set against an initialism ending in AI (yasai 野菜 / "Yet Another Shogi library, for AI"; shunsai 旬菜・俊才 / "SHogi's Ultra-fast Next-gen Successor, for AI"). The governing constraint was that **the name must not assert strength**: an engine that turns out weak should not be embarrassed by its own name, which removed 天才/甜菜 and 勝ち/価値. Also rejected, for reasons that generalize: 主菜 (one letter from shunsai — confusable in directory listings and tournament tables), 懐石/解析 (the best functional meaning of any candidate; lost on sound), 菜の花 (collides with the existing engine なのは), 捌き / 矢倉 / と金 / 雁木 (naming a technique or piece outright reads as a lack of invention rather than an allusion), 光彩/虹彩 (heard as 交際 first). Checked against the WCSC36 entry list — **not** against crates.io, which does not apply because these crates are `publish = false`.
  - **A new repository, not a reboot of `yasai`** — which was considered, since "Yet Another Shogi AI" re-reads the same letters. Two apparent obstacles turned out not to exist: yasai was never published to crates.io, and `tsumeshogi-solver` pins it by git *tag*, which survives anything done to the branch. What decides it is that replacing the tree leaves GPL code in the history. That is legal — the new tree would not be a derivative — but it leaves a path for a helper to be lifted out of an old commit, and that mistake is invisible after the fact. Eliminating the surface is worth more than the pun to a project whose top rule is licensing. Secondarily, the lineage would read yasai → shunsai → yasai2. **This is the judgement shunsai already made**: yasai was rewritten rather than relicensed, for the same reason.
  - **Released-version dependency, replacing the git-pin scheme this plan originally assumed.** A release per API addition was assumed to be a cost worth avoiding. It is not: shunsai is a library with third-party value and belongs on crates.io regardless, and cutting a release when E1 adds `attackers_to` is ordinary maintenance. Consequence: **shunsai v0.1.0 is a prerequisite of E0**, and E1's API additions each carry semver.
  - **Networks and self-play data stay out of git** (DESIGN.md §4), with the registry and manifests standing in for them. **Crates are split on demand** (DESIGN.md §4), and the layout changed in two places from the original sketch: one binary rather than two, and runtime network loading rather than `include_bytes!` by default.

(1) skeleton + USI shell, (2) material evaluation + iterative-deepening αβ, (3) TT + quiescence + `bench`, (4) repetition and 連続王手, (5) time management, (6) `openings-v1`, (7) match harness + SPRT. The ledger lives in [PROGRESS.md](./PROGRESS.md), which also carries the shunsai constraint sheet so a session need not re-survey the API. Ordering is forced in two places and otherwise free: `bench` (3) has to follow a search that produces node counts, and `openings-v1` (6) has to precede the SPRT harness that opens from them.
  - **The dependency is a git rev, against DESIGN.md §2 and against shunsai's own log.** shunsai's DESIGN.md moved "publish v0.1.0" from *Later* to a prerequisite of E0 on 2026-08-04, on the reasoning that the engine depends on releases rather than pins. That still stands and is not revised here; what is recorded is that E0 started before it happened, with `rev = "e58c16f…"` — a full commit hash, never a branch, matching `../benchmarks`' pin policy, over https so CI fetches anonymously. **The condition that reverts it is simply the release**, and it is an E0 exit criterion rather than a note: `git grep 'TODO(shunsai-0.1-release)'` finds every mention, of which four are things that change (PROGRESS.md lists them), one is a `cargo deny check sources` failure that clears only when the switch is complete. The API surface used is the four `pub use`s, so the switch is a manifest edit. Measured cost of the deviation: none yet — but it is worth stating that **no SPRT number may be recorded against a git rev that is not also a release**, because a rating series has to name what it measured.
  - **`shunsai = "0.1"` plus `[patch.crates-io]` was checked and rejected**, not assumed unavailable. It does work for a crate that was never published (cargo's own testsuite covers it). It loses because the manifest would assert something false, because `[patch]` is honoured only at the workspace root — so `rinsai-search/Cargo.toml` would stop saying where shunsai comes from, which is the one fact DESIGN.md §4's layering rule exists to make visible — and because a patch keeps silently overriding the real crate once it is published, so nothing goes red when the switch is due.
  - **`Game` delegates its record-keeping half to `shogi_core::Position` rather than reimplementing it.** The first draft carried `initial` + `partial` + `moves` by hand — which is field-for-field what `shogi_core::Position` already is (`{ initial, inner, moves }`, with a `make_move` that advances the board and pushes the move). The cause is worth recording because it generalizes: `shogi_core::Position::from_usi` had been rejected for mishandling the `moves` list, and that conclusion was then widened into "this type is not used", which is a different claim. **"We cannot parse with it" is not "we cannot store in it."** The wrapper itself remains necessary — the search-facing board has to be shunsai's, the only one with unmake and an incremental key, and `HistoryEntry` has no home in `shogi_core` — but it is now three fields rather than five, with one hand-maintained invariant fewer. `shogi_core::Game` was checked at the same time and is genuinely not useful here: it is `Position` plus a `GameResolution`, i.e. how the game ended, which may become relevant at E2's declaration handling and is not before then.
  - **A correction to the record, because a wrong reason outlives the decision it justified.** "`shogi_core::Position::from_usi` never reports an error" was stated in this log and in the code, and it is false — a malformed move token does produce one. Measured behaviour: a well-formed move that *cannot be made* (nothing on the from square, wrong side to move) is **silently dropped** and success is reported; a move that is structurally fine but **illegal** — 二歩, moving into check — is **applied**, since `make_move` documents that it never checks legality. Both still disqualify it for the `moves` list, so the decision is unchanged, but the reason now matches what the function does, and `crates/rinsai-search/tests/shogi_core_from_usi.rs` asserts it side by side with rinsai's own parser so the day `shogi_core` changes, the test fails and this is revisited rather than inherited. The habit this enforces: **a rejection recorded from a source reading, not a measurement, is a claim rather than a finding** — the same standard DESIGN.md §8 sets for performance work, applied to design decisions.
  - **Two audit passes over step 1, and what they say about how this project should work.** The first pass was told to find claims asserted without measurement; it found a latent bug (an option table dispatching on control *kind*, so adding `Threads` at E2 would have silently written into the hash size), two tests that could not fail, a CI guard that missed the ordinary way to enable a dependency feature, and a citation to a shunsai document that says nothing of the sort. The second was told to find correctness defects in concurrency, parsing and the protocol state machine, and found five, of which **two let any GUI or server end the process with one line**: a hand count no shogi set contains (`19P`) reaching shunsai's `[u64; 19]` Zobrist table, and a single non-UTF-8 byte — a CP932 path from a Japanese Windows GUI — being read as an I/O error and exiting the engine with status 0 and an empty log. It also found that a panicking search killed the worker while the engine went on answering the handshake, never moving, and finally exiting 0: from a match harness, indistinguishable from a game lost on time. Each was reproduced before being fixed and now carries a regression test.
    - **The generalisation is about where these came from.** None was subtle. All of them lived in the layer between "the code compiles and the tests pass" and "someone hostile, or merely foreign, is on the other end of the pipe" — a layer that has no perft to check it and, for E0, no SPRT either. DESIGN.md §8's measurement loop is the instrument for *strength*; it says nothing about robustness, and the first two audit passes are what stood in for it. **Every protocol surface should get one before it is trusted**: the CSA client at E2 will take input from a server rather than a local GUI, and E3's network loader will take a file path from an operator.
    - **The habit, stated for the sessions after this one**: a rejection or a guarantee recorded from *reading* source is a claim, not a finding — the standard DESIGN.md §8 already sets for performance work, applied to design and to robustness. A "sabotage" note saying which test catches a mutation is only worth writing if the mutation was actually made and the test actually went red; one that cannot fire is worse than none, because it is trusted.
  - **Step 1's own result, recorded because a measured outcome is a result**: rinsai speaks USI and plays legal games. Against the local material-evaluation YaneuraOu at `NodesLimit 10000`, 22 plies to a resignation with no illegal move and no protocol stall. It has no search, so this says nothing about strength — the ladder starts at step 2. One real bug came out of playing that game and not out of the conformance suite: the protocol thread had no way to learn that a search had *finished*, so every `go` after the first read as a protocol violation. The dialogues could not catch it, because they feed a whole script at once and a genuine overlap is indistinguishable from the bug; the regression test therefore plays a properly sequenced game through the real binary and requires stderr to be empty. **Recorded as a testing lesson, not just a fix: an in-process protocol test cannot see a bug whose symptom is timing between two threads.**
- **2026-08-06 — A review pass over step 1 before merge, and the one thing it says about the two audit passes before it.**
  - **A test case had been disabled rather than fixed.** `game.rs`'s "a position no shogi set could reach" table listed six SFENs and iterated `.take(5)`, so the sixth — carrying the comment *"Promoted pieces count as what they were"* — never ran; enabling it fails, because 17 pawns in hand is a legal position and the case was simply wrong. The property it claimed to cover, the `unpromote()` in `check_piece_counts`, was therefore untested: that line could be deleted with the suite green. Replaced with a case that actually exercises it (a `+P` on the board plus 18 in hand is nineteen pawns) and verified by making the mutation and watching it go red. **This is the failure mode the second audit pass named one bullet above** — "a sabotage note that cannot fire is worse than none, because it is trusted" — occurring in the same commit that wrote the warning. A `.take(n)` over a literal array is worth treating as a smell of its own: it silences by position, leaves the silenced case in the file looking covered, and no lint sees it.
  - **The piece-count bound missed the one kind that cannot change sides.** Kings were capped at two *per set*, which admits two black kings and no white one — the same class as `19P`, a position no set can produce reaching shunsai. Now capped per colour, and at *most* one rather than exactly one: a 詰将棋 diagram routinely omits the attacking king, `king_square` returns `Option` with `None` documented as legal, and rejecting those would cost a GUI an ordinary analysis question for no safety gained.
  - **`SearchDriver::shutdown` stopped one search and joined on all of them.** It remembered only the most recently submitted job's signals, so with two jobs in flight — the worker is a single FIFO, so the second queues — it raised `stop` on the one that had not started and then blocked forever on the one that had. Unreachable through `usi::run`, because `Engine::go` stops the previous search first; reachable by anything else, and `SearchDriver` is public API whose second caller is E3's self-play driver. Now holds a `Weak` per outstanding job and stops all of them. **The lesson is about where the invariant lived**: "at most one search in flight" was true of the protocol layer and assumed by the driver, and nothing wrote it down or checked it. A guarantee that holds only because of a caller's discipline belongs in that caller's type, or in an assertion.
  - **Three doc comments outlived what they described**, and the first was created by an *earlier fix in this same branch*: `parse_line` still credited `BufRead::lines` with stripping the CRLF, three commits after the loop moved to `read_until` precisely so that `lines` would stop being used; `shutdown` claimed to drop a queue that `mpsc` in fact still delivers; and `Game::clone`'s cross-check of the incremental Zobrist key against a from-scratch rebuild is a `debug_assert`, so it does not run in the release binary that plays — which the comment, and the pull request describing it as free on every `go`, did not say. **The cause is structural and the rule that came out of it is now CLAUDE.md §4**: step 1 copied each of its main arguments into four or five places, and a fix updates the copy it is standing next to. The argument lives in PROGRESS.md or in this log; the code carries the conclusion. Sabotage notes are the deliberate exception, because they have to sit on the test they describe.
  - **`cargo doc` joined CI and immediately failed**, on an intra-doc link to a private item added in the last commit of the branch. Doc comments are this project's design record and they link into it; nothing was checking that the links resolved. Also added: `cargo deny check advisories` — the only choice in `deny.toml` that had no recorded reason either way — and `|| true` on the `shogi_core` count guard, which under `bash -e` exited on a zero count *before* printing the message that is the guard's entire purpose (measured, not read).
  - **The generalisation, and it is not "audit harder".** All three audit passes were adversarial and all three were useful, but the defects above are ones a reviewer finds by *re-deriving a claim from the code* rather than by looking for bugs: a `.take(5)`, a bound of two where the domain says one each, a `Mutex<Option<_>>` where the prose says "any". The instrument for these is not another sweep with the same brief — **it is checking the claims the previous sweep left behind**, because a fix ships with fresh unverified prose attached and that prose is trusted precisely because it was written during an audit.

  - **The step-1 seam held, which is the result step 2 was asked for.** `Searcher::search` takes `&SearchJob` and `Game` hands out no `&mut Position`; the searcher asks `Game` for a board of its own instead, and neither signature moved. Six lines in `crates/rinsai` were **forced** to change and every one of them names the searcher or points at where it lives — two in `main.rs`, four in `tests/usi_conformance.rs`, none in `tests/usi_process.rs` — and every pre-existing conformance and process test passed unmodified. **Recorded that way, and not as "nothing else changed", because that is false and was written anyway**: step 2 added eighty-odd lines of new tests to the same file, which nothing compelled. A seam is verified by what a change *compels*, and the first draft of the entry stated the diffstat instead — caught in review, and worth keeping as the shape of the mistake, since the looser sentence is the one that reads as a stronger result. What did change is the *reason* recorded for `Game::search_board`: PROGRESS.md justified rebuilding the board by the cost of deep-copying shunsai's undo stack, and on the USI path that cost does not exist, because `usi.rs` already hands the job a `Game::clone`. The real reason is that `SearchJob` is public and E3's self-play driver is its second caller, so the search's requirement must not depend on how the job was assembled. A right decision resting on a wrong reason is one refactor away from being deleted.
  - **"Delete a surface step 2 does not use" is replaced by "keep it if its caller can be named."** The step-1 exception recorded below let `score.rs` freeze the negamax sign, the centipawn scale, the mate band and `MAX_PLY` with no caller, and set itself a test: anything step 2 does not reach for was built too early. Step 2 reaches for none of `clamp_to_eval`, `Score::NONE` or the four arithmetic impls — and deleting them is the wrong call, because each has a *specific* named caller one or two steps out (step 3's empty TT slot, E1's aspiration widening, E3's scale conversion). The rule now is that a callerless surface stays only if the caller can be named and the name goes in the doc comment. "It'll probably be useful" is what the audit was against; a named caller is a record, not a wish. `Score::NONE` additionally gained a warning, because it is a trap rather than merely unused: it compares as +32 002, above `INFINITE`, so seeding a maximum with it means the comparison never fires and the search silently keeps its first candidate.
  - **TT move ordering moves from E1 to step 3, with the table itself.** E1's list opens with "TT move ordering", which would leave steps 3 through 7 — including the SPRT harness bring-up — running a search with no ordering at all, and a transposition table whose move nobody tries first is half a table. MVV-LVA, killers and history stay at E1: those are interior-node heuristics and each wants its own SPRT. Root-only reordering landed in step 2 as part of iterative deepening rather than as move ordering, for a measured reason: without re-seeding the root list with the last iteration's answer, an iteration cut short reports the best of whatever prefix it happened to reach — measured worse than the completed iteration it replaced by the margin in PROGRESS.md's table, in the drop-heavy middlegame fixture. Node counts from the initial position fell 37% at the same time.
  - **DESIGN.md §8's measurement loop does not exist yet, and E0 should stop implying it does.** The standing form of this is "There is no instrument for strength during E0" below; what is decided here is that E0's own text has to say so, rather than leaving each step to discover it. Relatedly, DESIGN.md §5's "TT and quiescence search from the start" and the seven-way split contradict each other: step 2 ships the horizon-effect-prone thing DESIGN.md §5 says not to ship. The split wins, because step 3's diff is then cleanly attributable — but PROGRESS.md now says out loud that step 2's engine is *supposed* to look bad tactically, with the fingerprint to recognise it by (odd depths report exactly one pawn's board value plus one pawn's hand value more than even ones).
  - **Two bugs, and both were found by driving the release binary rather than by any test.** `DEFAULT_DEPTH` was being applied as a ceiling over *stated* budgets as well as over the "nothing was named" case, so `go movetime 1000` thought for four plies and handed back the other 975 ms. Every unit test named a depth, so every unit test missed it. And a conformance dialogue turns out to be structurally unable to hold a deep search open at all: `usi::run` reads the whole script at once, so `quit` reaches `shutdown` microseconds after `go` and **every dialogue in that file — `go movetime 1` included — is answered from the depth-1 iteration**. That invalidated two tests written for this step, one of which was worse than useless: `the_bestmove_is_the_head_of_the_reported_pv` compared two values that come from the same expression in the searcher, so reversing the principal variation left it green while the engine played a move from the middle of the line. Both moved to where depth is available. **The habit this reinforces is this log's own from one entry above** — a sabotage note is only worth writing if the mutation was made and the test went red. Twelve were made for this step; two named the wrong test, and finding that out is the only reason the notes are worth anything.
- **2026-08-07 — Review of E0 step 2, and the one rule it changed: a measurement does not go in a doc comment.**
  - **No defect was found in the search itself**, and the things worth not re-deriving next time are these. The **root's returned value is exact**: β is `INFINITE` so the root never fails high, and its children enter with α at `-INFINITE` so they never fail low — which is what makes the early break on `score.is_mate()` a break on a proof rather than on a guess, for a loss as much as for a win. **`pv[0]` can only ever be assembled from exact children**, because a child that fails high scores at most α at the parent and so never reaches `update_pv`. That last induction has one step that looks like a counterexample and is worth stating, because it is where re-deriving it goes wrong: a child that fails **low** *does* reach `update_pv` at its parent — it hands the parent a score at or above β — but doing so cuts the parent, so that parent is itself fail-high and its line never lands on a published one. The truncated lines exist; none of them surface.
  - **A correction to the entry above, made during its own review, and the failure mode is the entry's own subject.** It first read that "depth 1 always completes" holds *because* `self.nodes` accumulates across iterations rather than resetting. That is wrong: depth 1 is the first iteration, `self.nodes` is 0 when it starts either way, and `1 + N ≤ 594 < 1024` is sufficient and complete on its own. Two true facts had been welded together with a causal claim that is not, and left as written the next reader concludes the depth-1 guarantee would break if the counter were ever reset per iteration. What accumulation **actually** protects is a separate and real property: **in a sparse position the poll starves without it.** Measured on two lone kings — `4k4/9/9/9/9/9/9/9/4K4 b - 1`, about five legal moves a side — the nodes spent *in each iteration alone* stay under the 1024-node poll interval all the way through depth 6, while the cumulative count crosses it partway through depth 6 (PROGRESS.md carries both series). Reset per iteration and the poll does not fire once through depth 6, so `stop` and any deadline are ignored for that whole stretch; accumulating, it first fires partway through depth 6. **Both facts belong in the record and the arrow between them does not** — which is precisely the "inherited and trusted because it was written during an audit" shape this entry is otherwise about, arriving inside the audit that named it.
  - **A timing was written into a doc comment and had already drifted by 2× before anyone read it.** `negamax.rs` said depth 4 in the drop-heavy fixture takes about 30 ms; PROGRESS.md's table said 62 ms. Re-measured, it is about 40 ms. The two copies were wrong in different ways, and neither was wrong in a way its own reader could have noticed: the doc comment was a real measurement of a *different tree* — taken before the root re-seeding moved that position's depth-4 node count by the amount PROGRESS.md's table records, and never revisited — while the 62 ms was a real measurement of the first run after a build, which costs a fixed extra amount PROGRESS.md records and is paid once per *build* rather than once per process (PROGRESS.md carries the measurement and the two experiments that separate it from the explanations it otherwise fits — reversing the row order, and absorbing the whole penalty with a throwaway `--version` exec). A stale number and a first-run sample, indistinguishable from each other and from a good figure once written down.
  - **And a third time, from the direction the entry had not named: a number arriving from a *reviewer*.** The `508 980` above first went into this log as `508 976`, quoted from the review that caught the timing bug — pattern-matched off `838 976`, and taken on trust precisely because it arrived inside a careful audit. It was re-derived here by deleting the three re-seeding lines, rebuilding release and re-running the position; the same review then caught the digit. So the rule has a third clause. Prose written during an audit is trusted because of where it came from; **a number handed over by a reviewer is trusted twice over**, once for that reason and once because someone else appears to have done the work. Neither is a reason. Re-derive it or attribute it, and the attribution is not a substitute. The step-1 rule ("a rationale has one home") was written for *arguments*; it now covers **numbers**, and more strictly, because an argument goes stale visibly and a number does not. Timings are out of the source entirely; the code carries the conclusion (`DEFAULT_DEPTH` is four because the tree is close to a full minimax) and points at the table. What the re-measurement also showed is worth keeping: **the node counts reproduce to the digit across runs and the times do not** — the spreads are in PROGRESS.md's table, and this entry deliberately no longer carries a second copy of them, because the copy it did carry had already drifted from the table by the time anyone compared the two. Those are two different kinds of fact sharing a table, which is exactly why DESIGN.md §8 makes a quiet machine a precondition — noise cannot move a node count and can invent a time.
  - **`negamax_root` cannot tell a fail-low from an abandoned iteration, and `Window::open`'s doc was inviting E1 to find that out the hard way.** It returns `None` on "no root move raised α", which coincides with "no root move finished" only while α starts at `-INFINITE`; the doc nonetheless advertised that the method "already takes the window as a parameter so that" aspiration search could narrow it. It cannot: a fail-low would return `None` and `Searcher::search` would break out of the deepening loop instead of re-searching, with no wrong answer, no panic, and no failing test — every test here searches an open window. A `debug_assert` now pins the contract and the doc names what E1 owes the method. **The generalisation: a doc comment that promises a future caller is a claim like any other, and this one had never been checked against the code beneath it.** Same class as the three stale comments the step-1 audit found, arriving by the opposite route — not a comment outliving its subject, but a comment describing a subject that never existed.
  - **Two sentinels print as mate scores.** `Score::INFINITE` and `Score::NONE` both sit above the mate floor, so `mate_plies` answers `Some(-1)` and `Some(-2)` and an `info` line would spell `score mate -2` — the engine announcing a loss it never found. `Debug for Score` already special-cased both; `mate_plies` did not, and the asymmetry was the tell. Unreachable today, asserted against now. `Score::NONE`'s doc already warned that it is a trap rather than merely unused, and was one trap short.
  - **Time on the clock is not time on the wire, and only PROGRESS.md was in a position to say so.** DESIGN.md §5's list already assigns the network delay margin to step 5, correctly. But the risk it leaves lands on `movetime`/`byoyomi` — the budgets step 2 claims to honour *now* — and "honoured" was recorded without saying that the budget is spent to the last millisecond with nothing reserved for delivering the move. Step 2 played a game and PROGRESS.md recorded that it plays; the next reasonable thing to try is floodgate, where a byoyomi overrun is an immediate loss. No code change — the margin is step 5's and stays there — but the operating constraint is now written where someone about to do that would read it.
- **2026-08-07 — E0 step 3 becomes 3a and 3b, and quiescence lands. Three frozen conventions retired, and two of the step's own claims refuted by measurement.**
  - **The seven-way split becomes eight, and only here.** Step 3 was scoped as TT + quiescence + `bench` in one pull request. Building it showed the two halves are not one change: quiescence alone retires three frozen conventions, rebaselines every committed node count, and hollows out an existing sabotage note, while the table adds mate-score adjustment, PV-truncation rules and `USI_Hash` plumbing across a thread boundary. Landing them apart makes each node-count delta attributable, which matters more here than anywhere else because DESIGN.md §8's loop does not exist yet and node counts are the only instrument E0 has. Both of step 2's carried-in constraints survive the cut: `bench` still freezes counts *after* quiescence (it moves to 3b, which is after both) and the transposition move still ships *with* the table (both in 3b). Cost of the split, paid: about ten doc comments that said "step 3" had to say which half.
  - **Quiescence counts checked plies, not plies — and the first implementation got that wrong.** A single cap on total quiescence depth looks obviously right and is not. Swept on the drop-heavy middlegame at depth 4, a cap tight enough to save nodes fired its floor on a fifth of all quiescence nodes — which is a cap cutting *capture chains* off in the middle, i.e. the horizon effect reintroduced two plies down, paid for at full price. The two kinds of ply are not alike: a capture chain is self-limiting, because every capture moves a piece off the board and quiescence plays no drops, so occupancy strictly decreases; a check-evasion chain has no such argument, an evasion need not be a capture, and an evasion list is *every* legal move including drops. So only the checks are counted, and capture chains run to exhaustion. **The generalisation: a bound is only sound if it is a bound on the thing that is actually unbounded.** PROGRESS.md carries both sweeps.
  - **Two results from choosing that bound's value that nobody would have predicted from argument.** Allowing *zero* checked plies is not a cheap approximation but an incorrect engine — it evaluates while in check and misses a mate one ply away, reporting material. - **2026-08-10 — The USI layer is not shared with `tuishogi`, because an engine and a GUI need opposite halves of the protocol.**
  - **What the question turns on, and it is not how the code is factored.** `tuishogi` — a sibling TUI board, MIT, its own repository — reaches a phase where it drives an engine over USI, and the proposal was to extract whatever rinsai's protocol layer could lend it. The answer is nothing. USI is asymmetric: an engine **reads** what a GUI sends and **writes** its answers, and a GUI does exactly the reverse. The function that parses `go btime 1000` and the function that writes it are two functions, and having either does not give you the other. rinsai holds the engine half and only that, so an extraction hands `tuishogi` nothing it can call.
  - **So this was never "extract the USI layer".** It was "write a new crate holding both directions of both types, and retire part of the existing one into it" — the direction-neutral grammar is a minority of the four files, and the mirror halves exist in neither repository. A shared type is the *union* of both sides' needs rather than the intersection, and the union is visible already: `GuiCommand::GameOver` carries no payload because rinsai discards the argument, `GoMate` collapses its own, `Unknown(String)` exists so the loop can log what it ignored, and `Position(String)` is deliberately opaque. Each is small; together they are a permanent tax on both consumers, paid so that neither can have the type it wants.
  - **The GUI half is on crates.io, and rinsai cannot use it — the same fact from the other side.** `usi` 0.6.2 (nozaq/usi-rs) is MIT, depends on `itertools` and `thiserror` and nothing else, and **does not depend on `shogi_core` at all** — its moves are strings, which is what lets `tuishogi` take it without breaking its one-`shogi_core` rule. It offers `EngineCommand::parse`, `Info(Vec<InfoParams>)`, and `BestMoveParams { MakeMove, Resign, Win }`, the last carrying 入玉宣言, which is the shogi-specific thing a chess-derived codec would be missing. `usi/command.rs` already records why that crate is useless *here*: its `GuiCommand` can be written but not read. That sentence is exactly the reason it fits there.

    ⚠️ **Only its codec half fits.** Its engine driver is blocking and thread-based — `UsiEngineHandler::listen` takes an `FnMut(&EngineOutput) + Send + 'static` and spawns a thread, `get_info`/`prepare` block on `usiok`/`readyok` — and `tuishogi` is `tokio` with a single event channel. So the transport is `tuishogi`'s own either way, which is what its own phase-2 note ("the codec is separate from the process") already assumes. Read off crates.io and docs.rs rather than from source; the crate's last release is 2022, and it wants `itertools ^0.10` where `tuishogi` already has 0.14, so adopting it adds a second copy.
  - **What is genuinely duplicated, and it does not pay for a crate.** One thing: the drop-colour fix, since `shogi_usi_parser`'s `Move::from_usi` hard-codes every drop to Black and both programs rewrite it — a handful of lines each, and PROGRESS.md's shunsai constraint sheet already carries the trap. Everything that looks shared beyond that is transport: rinsai reads **stdin** with `read_until(b'\n')` and `from_utf8_lossy` because `BufRead::lines` errors on CP932, and a `tokio` consumer cannot share that code with a threads-only one anyway.
  - **The same asymmetry re-justifies `rinsai-protocol`, which DESIGN.md §4 had resting on the wrong thing.** Its stated reason was that the CSA client would want to share "the line-oriented loop" with USI. That loop is a few lines of framing, and CSA shares nothing else with USI — not the grammar, not the move notation (`+7776FU` against `7g7f`), not the state machine. What the two protocols genuinely share is the layer *underneath* both: the same `SearchDriver`, `Game` and time management, and the same "one answer per turn, structurally" invariant that `usi.rs` holds today. That is a session layer, not a codec, and it is what the crate should be split on. The row is reworded; the crate stays reserved for E2.
  - **Reopened when** a dialect bug found in one repository turns out to have a twin in the other, or a second Rust consumer of either half appears.

    ⚠️ **Whether rinsai itself grows one is unsettled in its own documents**, and this entry does not settle it: the "Threads, not async" record below says step 7's harness is Ayane in Python, while DESIGN.md §4 says the match harness and SPRT scripts are own code in this repository and puts `sprt` in `xtask`. Both can be true — vendored Ayane playing the games, `xtask` orchestrating it — but nothing records which, so a Rust USI *client* here is neither planned nor ruled out. Step 7 owns the answer. Until then this entry is about rinsai's own layer only, and says nothing about what `tuishogi` should conclude.

- **2026-08-10 — WebAssembly compatibility is kept as a constraint on the search core, and nothing is built for it.**
  - **The question was whether a browser build is reachable, and the surprise is that the toolchain says yes when the binary says no.** `cargo check` for `wasm32-unknown-unknown` passes today, unmodified, on stable. The release binary has no imports at all and a `main` that traps on `unreachable`: `thread::Builder::spawn` cannot succeed on that target, so LLVM folds the failure and deletes everything downstream of `SearchDriver::spawn` — which is the whole search. PROGRESS.md carries the figures and the surviving-symbol list. **A compiling target is not a supported target**, and the CI step added here is scoped to say so on its face rather than in a comment nobody re-reads.
  - **Three runtime traps, and the roadmap already owns the code around all three.** `thread::Builder::spawn` in `SearchDriver`; `Instant::now` at the **top of `NegamaxSearcher::search`**, which reads the clock unconditionally rather than only inside `Budget`, because the `info` line carries `time` and `nps` on every iteration; and `Condvar::wait` behind `wait_until_signalled`. Step 5 rewrites `Budget` for real time management and wants an injectable clock for its own tests regardless — a wall clock is not something a time-management SPRT can be written against — so the clock is its work rather than a separate task. E2 rewrites `SearchDriver` for Lazy SMP. Doing either seam early means writing it twice. The third is not a trap to fix but a subset to declare: `go infinite` and `go ponder` cannot work on one thread, so a browser session implements less than USI and says so.
  - **`catch_unwind` is inert there, and that is worth knowing before it is relied on.** The target is `panic = "abort"`, so the two nested catches in the worker catch nothing and the "a panicking search answers `resign` and the engine plays on" guarantee is a **native-only** property. The workspace profile's note about deliberately not setting `panic = "abort"` is true of the builds it describes and does not travel.
  - **What is already true, and what a first draft of this entry got wrong.** `Budget` honours a budget it was *told* and refuses one it would have to *decide*, so **the vocabulary** a browser needs exists: `depth` and `nodes` bound a search without a clock, and a host that owns the wall clock can size the next slice from the last. That is why CONVENTIONS.md gains a constraint rather than a work item.

    ⚠️ **It does not follow that the seam is ready, and this entry first claimed it was.** `Instant::now()` is the first statement of `NegamaxSearcher::search`, so `go depth 6 nodes 3000000` panics on wasm before it searches a node — the clock is read for the `info` line whether or not any budget wants it. An injectable clock is required, not merely available. The error is worth keeping because of where it came from: the clock trap was located by reading `Budget`, which is the only place a *deadline* lives, and the unconditional call one scope up was never checked. **A trap located by reading the type that owns the concept will miss the caller that reads it for another reason.**
  - **`web-time` was checked and not adopted.** It is `MIT OR Apache-2.0` and a genuine drop-in for `Instant`, but on wasm it pulls `js-sys` and `wasm-bindgen` and their trees into a lock file whose whole third-party set is three crates, every one of them provenance-scan surface. A `cfg`-selected clock adds none. **Adopted if** a browser build ever needs a deadline *inside* the engine that the host cannot express as depth or nodes.
  - **The honest ceiling, stated so it is not rediscovered at E3.** The E3 network's feature transformer alone is far larger than a browser download can be — PROGRESS.md carries the figure. Halving it would not change the conclusion, so compression is not the lever, and neither is GPU offload: **the constraint is download size, not arithmetic.** WebGPU is additionally the wrong instrument for *this* evaluation — NNUE's cost is an incremental accumulator update of a few columns, αβ evaluates positions strictly sequentially so there is nothing to batch, and a dispatch costs more than the whole evaluation. GPU is the right instrument for the E6 DL/MCTS branch and not for this one. So the browser build's **evaluation** forks from the native one, which is a fork the native design already has, since `EvalFile` exists precisely because networks are swapped without recompiling. The other seams — driver, clock, `catch_unwind`, the USI subset — fork too, and are listed above.
  - **Three E3 consequences that are free now and expensive later**, recorded here because E3 is where they land: the network's feature-set dimension belongs in the file header rather than a `const`, or a smaller net needs a second inference path forever; `EvalFile` should be a thin wrapper over a `load_network(&[u8])`, which a browser needs, self-play wants, and a filesystem path cannot provide; and every SIMD backend keeps a scalar reference implementation, which E3 needs anyway to test the SIMD against and which is what keeps a build without NEON or AVX2 possible at all.
  - **Revisited when** the browser stops being of interest, or when honouring the CONVENTIONS.md rule costs measurable Elo natively. In that case the native engine wins and the wasm build is dropped — it is a constraint accepted while it is free, not a goal with a claim on the roadmap.

- **2026-08-10 — E0 step 3b: the transposition table. Two predictions of this project's own refuted by measurement, and one pre-existing test found hollowed out by the change that hollowed it.**
  - **The table is built, the transposition move is searched first, and the ordering is the half that pays.** Measured across five fixtures and four depths (PROGRESS.md): searching the stored move first is worth between 1.00× and **14.02×**, super-linearly in depth. The scores are worth the rest. This is the concrete content of the 2026-08-06 decision that moved "TT move ordering" out of E1 and into this step — "a table whose move nobody tries first is half a table" was an argument then and is a number now.

  - **An in-window `Exact` cut was predicted to truncate the published line. It does not, and the prediction had already become a sabotage note before anyone checked.** The reasoning was sound as far as it went — a table cut returns after `pv[ply].clear()` and before the move loop, so the node's line is empty while its parent raises alpha without cutting. It has moved to the one fixture of five still measured to disagree, and it now asserts the disagreement *before* the assertion that depends on it, so the next time a change takes the discrimination away the test says so rather than going quiet. **A change hollowing out a test in the same commit is not new here — step 3a's quiescence did it to the move-buffer test — but it is the reason the re-run rule covers previously verified notes and not only new ones.**
  - **Three inputs to a node count are fixed rather than inherited, because each is otherwise a hidden variable in a baseline.** Table *size* moves node counts on its own — a bigger table evicts less — so `bench` sizes its own table instead of reading `USI_Hash`, and no count in PROGRESS.md is quoted without one. The table also survives a search by design, so `bench` calls `new_game` between positions or position *n* is searched against whatever 1..n−1 left behind, making the counts depend on the order of a file. And the depth is a constant. ⚠️ **This was learned from a test that failed for the wrong reason**: a first draft asserted that resizing the hash empties the table by comparing a search before and after a `1 → 2 MiB` resize, and the counts differed because of the *sizing*, not because anything survived.
  - **`bench`'s per-position counts live in the source, which is the one deliberate exception to "a number goes in a PROGRESS.md table and nowhere else".** A regression baseline has to be executable to be a regression test, and a copy of it in a document is a second copy that drifts — which is the failure the rule exists to prevent, arriving by the other route. What is in PROGRESS.md is the total and the conditions.
  - **Allocating the advertised default table costs about as much as a whole E0-depth search** — 6–21 ms against 13–20 ms for depth 6 from the initial position (PROGRESS.md). Harmless where it is, because it happens once per searcher and `isready` is allowed to take arbitrarily long, and worth recording only because the two figures being the same order is not obvious and a future change that moved allocation onto the `go` path would look free.
  - **`positions/` arrives here rather than at step 6.** DESIGN.md §4 dated the directory to `openings-v1`; `bench` needs a committed position set two steps earlier, and CONVENTIONS.md already named that set as where the licensing rule bites hardest. The set is `bench-v1.sfen`, every line carrying its provenance in the file's own header, and it is `include_str!`-ed so a count cannot depend on the working directory the engine was launched from.

- **2026-08-11 — Review of E0 step 3b. The table's own tests did not cover the one thing in it that is user-visible, and an option the engine advertises could kill the process.**
  - **The mate-score ply adjustment had no coverage at all, and the sabotage note said otherwise.** Deleting the `to_table` call from `store`, or the `from_table` call from `probe`, left the **entire suite green — `bench` included**. The unit test exercised the two free functions directly and never went through `Table`, so it could see a broken *function* and not a missing *call site*; and no bench position ever probes a mate entry at another ply, so the frozen counts did not move either. Live symptom would have been `score mate N` on a line that is not N plies long, and a search preferring the longer of two mates. The test now goes through `store`/`probe` and both mutations go red. **The generalisation, and it is a new one: a unit test on a helper does not cover the helper's callers, so a note naming "drop either half of the adjustment" was describing a mutation nobody had made.** The rule this repository already had — the mutation must be made and the test must go red — is necessary and was followed for the *function*; what it does not say, and now does, is that the mutation has to be made at the site the note is attached to.
  - **`USI_Hash` could abort the engine on a value the engine advertises.** The option declares `max 65536`, which reaches `vec![Entry::default(); 2^32]` — 64 GiB — and `vec!` is infallible, so a refusal goes to `handle_alloc_error` and aborts the process, from the worker thread, mid-tournament. That is the class the step-1 audit named ("one line from a GUI or a server ended the process") arriving through a new door, and it directly contradicts the error policy `usi.rs` opens with. The allocation is now `try_reserve_exact` with a one-MiB fallback and a diagnostic. **What made it easy to miss: the bound was checked against the *spec* (`min`/`max` are honoured, and there is a test saying so) and never against the machine.** An advertised maximum is a promise about behaviour, not only about parsing.
  - **`Score::NONE` is deleted.** Its doc named step 3b's transposition table as its caller; the table marks an empty slot with a zero `Bound` code so that an all-zero `Entry` reads as empty, and never used it. The 2026-08-06 entry that kept all six of `score.rs`'s callerless surfaces did so on the strength of naming a caller for each — this is the first of those names to be falsified, and CONVENTIONS.md's rule is that the surface then goes. Re-adding it costs three lines if E1's futility wants a "not computed" marker.
  - **Two more stale promises of the same shape, found by asking what step 3b was said to be going to do.** `usi.rs`'s `isready` comment said the transposition table was the slow initialisation belonging there; it is allocated in `main` and resized on the worker, so `isready` does nothing with it. And `bench`'s determinism test carried a sabotage note naming a mutation it cannot see, because `measure` builds a fresh searcher per call and any change that moves both runs alike leaves the two equal. **Three of the four prose defects in this review were forward promises written by an *earlier* step and left unchecked when the step they named arrived** — which is a cheap and repeatable review question: grep the diff's step number, and check each thing it was promised to do.
  - **What the review did not find.** Nothing wrong in the search: the window handling, the bound semantics, the mate-distance arithmetic itself, the transposition move's legality check and the principal variation's assembly were all read against the code and hold. Recorded because a review that finds nothing in the code is a result about the code.

- **2026-08-11 — E0 step 4: 千日手 and 連続王手, and a mate suite that reached further than the plan expected. Two of this step's own predictions refuted.**
  - **The rule is implemented at four occurrences, and the two-fold cut most engines use is deferred to E1 with its condition.** Scoring the *first* repetition on the search path as a draw is standard practice, it prunes cycles, and it is a **search heuristic** rather than the rule: 千日手 is four occurrences and nothing less. This log's own standing entry says there is no instrument for strength during E0, so a deviation from the rule cannot be justified here — it would be adopted on argument, which CLAUDE.md §3 forbids. It goes to E1, where one feature is one SPRT. **The consequence worth stating, because it shapes every test in the step**: twelve plies is more than an E0 search sees, so at these depths the fourth occurrence is reached almost entirely out of the *game's* history rather than from inside the tree. A fixture that can exercise this therefore has to carry a real move list; a bare `sfen` root cannot test repetition at all.
  - **The verdict is decided at the dispatch rather than at the top of the interior node, and the depth-1 iteration is what decides that.** `negamax_root` calls `child(depth - 1)`, so at depth 1 every root child is a *quiescence* node — and depth 1 is the iteration `Budget::without_limits` guarantees always completes. A check at the top of `negamax` would therefore leave the one iteration that always finishes unable to see the move that loses the game, which is the whole hazard. Two further properties fall out of the same placement rather than being arranged: the node is never entered, so a path-dependent verdict never reaches the transposition table's probe **or** its store, structurally rather than by a flag; and the node-counting convention ("one node per `search`/`qsearch` entry") needs no amendment, because a repetition cut-off is not an entry. `bench` not moving is the evidence for the second.
  - **Quiescence is a deliberate hole in the repetition path, the argument that permits it is narrower than it first looked, and it has an expiry date.** What it buys is the whole cost of the feature: quiescence is the overwhelming majority of all nodes (PROGRESS.md carries the share), so the `in_check()` per push and the scan per node are paid on the small remainder. What justifies it is that a quiescence subtree's *entry* position is one its interior parent already pushed, and a quiescence line cannot return to that entry — every ply but at most `QS_MAX_CHECK_PLIES` is a capture, a capture takes a piece off the board, and the only move quiescence has that puts one back is a drop from an evasion. ⚠️ **The first draft of that argument claimed more than it can carry, and this is the correction rather than the claim.** It was written as "a quiescence line cannot return to a position above it", which would cover the game's history too — and it does not: the path from a history position down to a quiescence node runs through interior moves that can do anything. So a quiescence position coinciding with an earlier *game* position is a fourth occurrence this search does not see. That is a known imprecision, of the same family as the two `qsearch`'s own doc already lists, and it is recorded rather than fixed. **The general shape is this log's oldest rule arriving in new clothes: a bound derived by reading is a claim, and widening one while shortening the sentence is how a claim becomes false.** ⚠️ **E1 item 8 ends the bound as well** — the moment quiescence generates checks and non-capture promotions, a quiescence node can play a quiet move. That item now carries extending the path into quiescence as part of its own work.
  - **A band of its own rather than the mate band, and flat rather than ply-relative.** A 連続王手の千日手 win is not a mate, and reporting it as `score mate N` would announce a mate whose principal variation does not deliver one — which `a_reported_mate_is_a_real_mate` exists to forbid. So there are three bands now: evaluations, then the repetition value, then the mates, with `clamp_to_eval` retargeted at the lowest of the two upper ones so that E3's network scale cannot climb into either. It carries **no distance to the root**, unlike a mate score: a repetition verdict is never stored, so nothing needs to adjust it, and keeping it flat leaves the table's mate-by-ply adjustment the only ply-relative score in the engine — one mechanism rather than two.
  - **⚠️ The prediction that `bench` would need re-freezing was wrong, and it could not have been right.** PROGRESS.md's step-4 note said to expect `the_frozen_counts_are_what_the_search_produces` to fire. It did not: every count is identical to the digit and the total is unchanged. The reason is the one above — the seven committed positions carry histories one to seven plies long, and a depth-4 search cannot reach a fourth occurrence from any of them. Recorded because the prediction was written down. ⚠️ **And not as evidence of anything else** — an earlier draft of this bullet offered the unchanged counts as proof that the verdict stays out of the transposition table, which the sentence before it refutes: if no fourth occurrence is reachable in `bench`, no verdict fires there and nothing could have been stored either way. An experiment with no treatment arm is not a measurement.
  - **⚠️ The prediction that mate-in-4 and mate-in-5 would be out of reach was also wrong, and by two orders of magnitude.** The plan reasoned from branching — nine plies of full-width search with only transposition-move ordering — and concluded the deep rows would not fit in `cargo test`. Measured, the deepest row costs under twenty thousand nodes and the whole ladder a few milliseconds in the *dev* profile (PROGRESS.md carries the table). The arithmetic was not wrong about full-width search; it was wrong about the position, because a forced mating sequence is exactly the input alpha-beta prunes best. **The generalisation is one this log keeps arriving at: a cost predicted from branching alone is a claim, not a finding** — and the cheap way to find out was to build the fixture and search it, which took less time than the estimate did.
  - **打ち歩詰め is what makes a mate ladder hold its length, and that was found by a ladder collapsing.** The suite's five distances come from one board and one parameter: a pawn in White's hand is a move of mate. Built first with *golds* in hand, the mate-in-5 row answered `mate 5` instead of `mate 9` — because Black captures whatever is interposed and may drop it straight back, and a gold dropped beside the bare king is mate on the spot. A pawn dropped there is 打ち歩詰め and illegal, so with pawns the ladder holds. A shogi-specific rule doing load-bearing work in a test fixture, and the reason the fixture's doc says which piece and why.
  - **Mutual perpetual check falls to a draw, and it is reachable rather than theoretical.** At most one side is in check in any legal position, but the two runs the verdict tests are over *different* positions, and an evasion may give check back — so both sides can be checking on every one of their own moves. The rule names one loser and has no answer for two. Recorded rather than left to a reader who will otherwise re-derive that the case is impossible, because it is not.
  - **The known imprecision this leaves, stated rather than fixed.** A node whose *child* returned a repetition verdict stores a score derived from it, and that score is path-dependent while the table is keyed on the position alone. Every engine lives with this. Not fixed here because the fix — propagating a "this subtree saw a repetition" flag up and declining to store — is a separable search change with a node-count cost and no instrument at E0 to weigh it. Revisited when E1 item 11 puts quiescence in the table, or when E2's Lazy SMP shares one.
  - **The sabotage re-run found a second reachable line in `negamax` that no test can see, and three notes were describing mutations nobody had made.** Fifty-nine mutations, each applied at the site its note names, whole suite run against each; PROGRESS.md carries the tally and the four findings. The largest is that `negamax`'s own `mated_in(ply)` can be scored `mated_in(0)` with the **whole suite green, `bench` included**, while the same mutation in `qsearch` fires all three tests whose notes name it. The cause is the one that also makes the mate ladder cheap: quiescence runs past the nominal depth, so a mate that surfaces is resolved there first and the deepening loop breaks. **That gives the 2026-08-09 entry's `pv[ply].clear()` finding a sibling, and the pair is a shape rather than a coincidence** — the interior node is the one whose results are most often pruned away, so its arms are the ones hardest to observe. Neither line is dead; both are unfalsifiable, and PROGRESS.md is where a future "delete the dead line" checks itself.
  - **⚠️ Four of the sweep's own mutations were defective, and two of those failed *silently*.** Two did not compile, which announces itself. The other two changed the source text without changing the behaviour — one replaced `DEFAULT_HASH_MB` with the literal `256`, which is what it already equals; the other only added a comment. **A no-op mutation reports GREEN and is indistinguishable from a false note**, so a sweep that does not check its own mutations manufactures exactly the finding it exists to detect. This is the "re-run every sabotage" rule needing a rule of its own, and it arrives the same way every previous refinement did: by nearly producing a wrong conclusion. The check that would have caught both is cheap — a mutation that leaves every test green should also leave `bench`'s node counts *unchanged* only if it plausibly could, and neither of these could.
  - **`Game::clone`'s Zobrist cross-check stays a `debug_assert`**, which is the question the entry below under "Two branches with no test" parked for this step. The concern was real: the history's keys come from `HistoryEntry::of(&self.board)`, i.e. shunsai's *incremental* key, so a drift would corrupt a repetition verdict directly rather than merely the SFEN. What settles it the other way is the cost of the alternative. `Game::clone` runs on the **protocol thread**, once per `go`, so a real assertion puts a panic there — and `usi.rs` opens by promising that bad input never stops the loop, while the step-1 audit's worst findings were both "one line ends the process". Trading a quiet wrong verdict for a dead engine is not a trade this project's error policy makes. Meanwhile the check does run on every `Game::clone` under `cargo test`, which is every conformance dialogue and every search test in the suite. **Revisited if** an incremental-key drift is ever actually observed, or when E2's CSA client starts using the record for an in-game decision.

## Recorded but deliberately not built

[CLAUDE.md](./CLAUDE.md) forbids building for a consumer that does not exist
yet, and requires recording the condition instead. These are those records —
subject-ordered rather than dated, because each is a standing condition rather
than a moment.

### The named-caller rule, and the one surface that earned an exception

`score.rs` went into step 1 with no caller at all. The exception was deliberate
and narrow: **a type that exists to freeze a convention is not speculative
building, because the convention is what the next step is about to depend on.**
Negamax sign, centipawn scale, the mate band and `MAX_PLY` are decisions step 2
would otherwise have made implicitly, and the cost of getting one wrong is a
class of sign bug that SPRT reads as "that patch was bad". That half held: step
2 uses every one of them.

The *test* step 1 wrote for itself did not. It said: if a step-1 type has API
that no step-2 caller uses, it was built too early — so delete `clamp_to_eval`,
`Score::NONE` and the four arithmetic impls at step 2. Step 2 uses none of the
six. **The rule is now:**

> A surface with no caller stays if — and only if — a *specific* caller can be
> named, and the name goes in its doc comment. Otherwise it goes.

"It'll probably be useful" is what produces the state this audit exists to
prevent; a named caller is a record rather than a wish, and re-adding three
lines later is not the expensive part. All six can be named — `Score::NONE` is
step 3b's empty transposition-table slot, the arithmetic is E1's aspiration
widening and step 3b's mate-score-by-ply adjustment, `clamp_to_eval` is E3's
network scale conversion — so all six stay, each carrying its name.

`Score::NONE` additionally carries a warning, because it is an active trap: it
compares as +32 002, above everything including `INFINITE`, so using it to seed
a maximum means `if score > best` never fires and the search silently keeps its
first candidate. `Option<Score>` is the right shape and the search uses it.

**A named caller that does not turn up is also a result, and step 3a produced
one.** `MAX_PLY`'s doc said the search's per-ply state would gain a static
evaluation "from step 3", which is why step 2 declined to write the `Stack`
struct for what was still a one-field array. It did not happen: quiescence
computes its stand-pat as a local and nothing reads it again, so per-ply state is
*still* exactly the principal variation. The `Stack` struct is deferred to E1 —
killers (item 3) or futility's per-ply static evaluation (item 9), whichever
lands first — and the trigger is written as "the first *second* field" rather
than as a step number, since a step number is what went stale here. The doc has
been corrected; the prediction is kept because a prediction that failed is worth
as much as one that held.

The rule as it now stands is in [CONVENTIONS.md](./CONVENTIONS.md); the argument
that produced it is the second 2026-08-06 entry above, on E0 step 2.

### The move buffer — decided in step 1, built in step 2 as recorded

Built as specified: a **shared, ply-threaded `Vec<Move>`** reserved once at
`MAX_LEGAL_MOVES * MAX_PLY` elements, sliced per ply, generation appending and
the caller truncating back. shunsai's own `perft_materialize` shape
(`examples/perft.rs:71`). The rejected alternatives, still the reasons:

- **`ArrayVec<Move, 593>` per ply on the stack** — same size but *per node*.
  `Move` has no `Default`, so an `unsafe`-free version needs a dummy fill, and
  avoiding that means `MaybeUninit`, which the workspace denies.
- **`Vec<Move>` per ply** — one malloc/free per node.
- **A ply-indexed array inside the search stack** — where E3's accumulator stack
  goes, but it makes the move list borrowed while recursing on `&mut stack`.

Two things the decision did not say, learned from building it. The buffer hands
out **moves by value, never a slice** — a slice borrows the buffer across the
recursive `&mut self` call and does not compile. And **forgetting to truncate is
a leak, not a wrong answer**: every ply reads its base before generating, so no
ply ever sees another's moves. `MoveBuf`'s own tests therefore cannot catch a
missing truncate; `negamax::tests::the_move_buffer_comes_back_empty` is what
does, and the sabotage was run to confirm it.

The original note put the buffer at 593 × 3 B × 128 ≈ 222 KiB. `Move`'s layout
is not something Rust guarantees, so the reservation and its test are both in
**elements**.

At E1 the element becomes scored — either a parallel score array indexed
identically, or a `ScoredMove`. `get` keeps its signature either way, so the
search's loop does not change shape.

### `[patch.crates-io]` for an unpublished crate — checked, and rejected anyway

It **does** work: cargo's own testsuite covers it
(`tests/testsuite/patch.rs::nonexistent`), and the Cargo book says sources can
be patched with versions of crates that do not exist. Rejected on three grounds:
`shunsai = "0.1"` in the manifest would assert something false; `[patch]` is
honoured only at the workspace root, so `rinsai-search/Cargo.toml` would stop
saying where shunsai comes from; and a patch would keep silently overriding the
real crate once it is published, so the switch we are trying not to forget would
never go red. Recorded so it is not re-opened.

### A `quit` watchdog — still not yet, and now for a better reason

The step-1 note said the open risk was "a step-2 search that ignores `stop` — an
infinite loop with no poll". Step 2's search polls, `an_infinite_search_stops_when_told`
proves it, and removing the poll is one of the sabotage mutations that goes red.
So the specific hazard is closed and a watchdog is still not needed. If one is
ever added it should be a **bounded wait** in `shutdown` rather than a
`process::exit`: an unconditional exit would make a hung in-process conformance
test *pass*.

### `quit` stops the search, and that shapes how the engine can be tested

`usi::run` reads its input as fast as it arrives, so in `printf … | rinsai` the
`quit` reaches `shutdown` microseconds after the `go` and the search returns
whatever depth 1 gave it. That is correct — `quit` means quit — but it has two
consequences worth writing down, because both were discovered the hard way:

- **Every dialogue in `tests/usi_conformance.rs` is really answered from the
  depth-1 iteration**, `go movetime 1` included. A conformance test cannot
  exercise a search of a stated size. Anything that needs one belongs in
  `rinsai-search`'s own tests or in `usi_process.rs` over real pipes.
- **Driving the release binary by hand needs a reader that waits for
  `bestmove`** before sending `quit`, the way a GUI does. A plain pipe measures
  nothing.

### `go ponder` starts its clock too early

A `go ponder movetime n` starts its deadline when the search starts, not at
`ponderhit`. Harmless at step 2 — the driver holds the answer back anyway and
the search simply finishes early and waits — but wrong, and E2 is where ponder
becomes real and this gets fixed.

### There is no instrument for strength during E0, and that is structural

CLAUDE.md calls the measurement loop the project's spine and DESIGN.md §8 says
it starts at E0. In practice `bench` arrives at step 3b, the opening set at step
6 and the SPRT harness at step 7, so **steps 2 to 5 cannot be measured at all**.
"One feature = one SPRT" is a rule about SPRT hygiene and it does not bite yet;
what the E0 step boundaries actually buy is reviewable diffs and isolated risk.
Worth stating plainly so that nobody reads E0's merges as measurement debt, and
so that nobody reaches for an SPRT number that cannot exist. Games against
`../benchmarks` during E0 are "it plays", never "it is stronger".

### Threads, not async — and no `tokio`

Asked and answered rather than assumed. The concurrency here is two threads: one
blocked on stdin, one running a search flat out. Async runtimes exist to wait on
many I/O sources cheaply, and this has exactly two (stdin, stdout) and one
long-running **CPU-bound** task — which under `tokio` would have to go to
`spawn_blocking`, i.e. back to a thread, having gained nothing but a dependency.

It gets less appealing with each phase, not more. E2's Lazy SMP is N OS threads
each searching at full tilt over a shared transposition table: the shape async
is specifically not for. E2's CSA client is **one** TCP connection, which a
blocking socket on its own thread handles with less machinery. E3's self-play
drives the search library in-process with no protocol at all. And `tokio` is a
large dependency in a project where every one of them is provenance-scan surface
(CLAUDE.md §2) — the whole tree is three third-party crates today.

The condition that would reopen it: something that has to wait on *many*
independent I/O sources at once inside the engine process. Nothing on the E0–E6
roadmap does. (The match harness at step 7 runs many engine processes, but that
is Ayane, in Python.)

⚠️ **The conclusion stands; one premise above is narrower than it reads.** "The
concurrency here is two threads" describes an engine that is an OS process with
stdio, which is every build this project ships. A browser build is neither — it
has no stdin to block on and no thread to give the search — and it does not want
async either, because it has nothing to wait on: the host calls in, the search
runs, the answer returns. So the wasm case is not a counterexample to this entry
and not an argument for a runtime; it is outside the situation the entry
describes. See the 2026-08-10 log entry and CONVENTIONS.md's Portability rule.

### A browser build — the shape it would take, and why none of it is written

The consumer does not exist: there is no web application to put an engine in.
What is built is the constraint (CONVENTIONS.md's Portability rule) and a CI
step that keeps the target compiling. The shape is recorded so that whoever does
build it is not re-deriving it, and so that step 5 and E2 know what they are
absorbing.

**Single-threaded, in a Web Worker, on stable Rust.** The search is called
directly — `Searcher::search` is already the interface and `SearchDriver` is
merely one caller of it — so the driver is bypassed rather than ported. The
threaded alternative needs `+atomics`, `SharedArrayBuffer`, COOP/COEP headers on
the host and `-Z build-std`, i.e. **nightly**: it buys Lazy SMP in a browser,
which is optimising the weakest build for strength, and it collides with the
`rust-version = "1.88"` discipline for the sake of it.

**Sliced by `go depth N`, with `nodes` as a cap.** The host owns the wall clock,
sizes the next slice from the last, and never sends `infinite` or `ponder`. Each
slice re-runs the deepening prefix. ⚠️ Whether that waste shrinks once a
transposition table exists depends on the table outliving a `go`, which is a
question for step 3b to answer rather than an assumption to inherit: today
`NegamaxSearcher::search` clears `nodes`, `seldepth`, `stopped`, the buffer and
every `pv` line at the top of each call, so nothing carries over at all.

**A string-in, lines-out interface** — `step(line) -> Vec<String>` — rather than
a typed JS API, so a web GUI drives wasm and a child process with one code path.
A typed API would re-encode `usi/command.rs` and `info.rs` into a second
protocol covered by one set of tests. ⚠️ **`tests/usi_conformance.rs` is not
that shape and cannot simply be reused.** It feeds `usi::run` a whole script and
asserts the transcript *after* the run returns, which works only because `run`
joins the search thread first; a per-line `step` returns before the worker has
written its `info` and `bestmove`. Two obstacles, not one: that, and `Engine`
being private and owning a `SearchDriver` concretely — a `Runner` trait with an
inline implementation is what E2 would add anyway.

**Built when** there is a web application asking for it. ⚠️ Not before: a
`cfg(target_arch = "wasm32")` branch nobody exercises rots faster than an absent
one, which is why the constraint and the compile check are the whole of what
lands now.

### `usi.rs`, not `usi/mod.rs`

Modules with children are `foo.rs` beside `foo/`, not `foo/mod.rs`. This is
shunsai's layout too (`src/sliders.rs` beside `src/sliders/`), so it is the
family convention rather than a preference — and it keeps editor tabs and greps
distinguishable, which is the reason the ecosystem moved.

### What a caught panic leaves behind

The worker catches a panic from `Searcher::search` and answers `resign`, which
keeps the engine playing rather than silently dead. The residual risk is named
rather than solved: a searcher that panicked may have left its own state
inconsistent — from step 3b that is a transposition table. `usinewgame` clears it,
and one bad game beats a dead engine, but if step 3b finds a way for a corrupt TT
to survive into the next game, this is the place to revisit.

### Two branches with no test, named rather than left to be discovered

- **`Engine::go`'s fallback for a gone worker.** `submit` returns `false` and the
  protocol layer answers `bestmove resign` itself, because it has already taken
  the `go` and owes exactly one answer. `SearchDriver` has a unit test that
  `submit` reports the failure; the *protocol* half has none, and with the outer
  `catch_unwind` now keeping the worker alive through any panic in the loop
  body, there is no longer a way to reach it from a dialogue. It is defensive
  code guarding an invariant, kept for that reason and untested for the same one.
- **`Game::clone`'s Zobrist cross-check is `debug_assert`.** It runs under
  `cargo test` and in a debug build, and is compiled out of the release binary
  that plays. The lockstep record is therefore a property the *suite* checks,
  not one a live game does. Step 3b is where to reconsider — and the framing it
